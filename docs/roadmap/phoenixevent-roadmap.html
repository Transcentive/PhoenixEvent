PhoenixEvent roadmap

The order of work for the new application, from the requirements baseline 0.1 and specification 0.75. This page shows the order and what each phase depends on. The baseline assigns no dates or durations until the architecture, staffing and release scope are known, so the timeline shows sequence only.

Status as of October 10, 2026: the design system and 59 wireframe screens are complete. The first release is scoped, and the six decisions it needs are settled. A review found four more to settle before Phase 1 starts, and all four are now settled. Of five to settle before their features are built, three are settled, the lookup on screen A1 is proposed, and the limit on participants is partly open (specification 16B.4). No code exists yet.

The phases in words

Each phase lists what it delivers and the condition for leaving it, as the baseline states them. A shaded box marks what the specification adds to the baseline.

Phase 0

Resolve foundational decisions

In progress
Delivers
A reviewed requirements baseline, lifecycle diagrams, the organization and session model, the permission matrix, the paid-access model, and the scope of the first release. Repository name, runtime versions and hosting targets.
Leaves when
The architecture and every outstanding assumption have been reviewed, with each proposal either confirmed or still marked as a proposal.
Recorded October 5 to 10, 2026. The first release is scoped: 10 of 21 features, on 33 of the 59 screens (section 16B). The six decisions it needs are settled. The stack is The Mighty Queue's (section 2A), with the design system's own stylesheet in place of Bootstrap. The repository is github.com/Transcentive/PhoenixEvent, and no Drupal data is used. Held for later: how one organization per browser holds at an organization's own address, and moving to a supported Node.js version. Settled before Phase 1: sign-in and deployment (2A.3), a separate account at each organization's address, usernames unique within an organization, and the Event Administrator as an organization setting.
Phase 1

Repository and development foundation

Yet to start
Delivers
The new repository with a modular Go and React structure, PostgreSQL migrations, typed database access, automated checks, configuration handling, first deployment notes, an email adapter and a file storage interface.
Leaves when
A repeatable setup on a plain Linux host works, the API and frontend build, migrations run, and health checks pass.
Phase 2

Accounts, organization context, and roles

Yet to start
Delivers
Accounts, username and email rules, email confirmation and password reset, login and logout, memberships, scoped permissions, and one active organization per session.
Leaves when
Access across organizations is refused in the API, the screens, files and session changes, and the login flows work against a test email service.
Wireframes
Accounts (A1 to A7), Organization (O1 to O7), States E1 to E3, Dialogs D5 and D6
Added: bodies and their members, and the five permissions for creating and approving events.
Phase 3

Events, boards, stations, and registration

Yet to start
Delivers
Events and their boards, role titles, chairs, capacities, registrations, station assignments, registration policies, optional waiting lists, and the organization's own terms for events and stations.
Leaves when
A realistic event can be set up and registered for, capacity holds when many people act at once, and waiting list governance is enforced.
Wireframes
Registration (1 to 9), Event setup (S1 to S9), Dialogs D1 to D4, Governance (G1 to G5)
Added, before events themselves: event creation rules, proposals, and approvals.
Phase 4

Public pages, announcements, media, and themes

Yet to start
Delivers
Public event pages that search engines can find, attachments, announcements at organization, event and station level, the warning before leaving the site, uploaded and embedded video, and the three themes.
Leaves when
Public and private behavior, downloads, outside links and accessibility are checked against the agreed limits.
Wireframes
Communication (C1 to C5), Dialog D7
Phase 5

Organization payment and individual payment

Yet to start
Delivers
Organization payment for the use of PhoenixEvent and for the participants it pays for, individual payment by subscribers, paid features, the payment provider, and a record of every payment change.
Leaves when
Both kinds of payment work with membership, payment and permissions kept separate, and a repeated payment notice cannot grant or charge twice.
Wireframes
Billing (B1 to B3)
Phase 6

Optional chat

Yet to start
Delivers
Conversations for the organization, each event, each station, and direct messages, with switching on by an authorized role, a paid plan as the key, and the agreed moderation and retention.
Leaves when
Live and past messages respect organization and session boundaries, logging out ends access, and the plan and permission checks hold.
Wireframes
Chat (H1, H2)
Phase 7

Release validation and direct deployment

Yet to start
Delivers
End-to-end runs, an accessibility review, organization isolation checks, load checks, a backup restore, upgrade and rollback practice, the installation guide in Markdown, HTML and PDF, and a staging deployment.
Leaves when
Required checks pass or each known defect is accepted in writing, the guide has been tested, and production is approved.
