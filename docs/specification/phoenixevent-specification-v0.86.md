## 1. Purpose and scope

Enable people to work together in an organization’s event, divided into stations or departments. Organizations include PTAs, community committees, banks, and businesses. Each organization controls its memberships, events, governance, registration policies, communication, and subscription access.

Use Event_Registration and event_station as behavioral references. Build a new codebase with Go as the backend language. Legacy Drupal code is a reference rather than an implementation dependency; known legacy defects must not be copied into the new application. Data migration from Drupal is not yet specified.

The application must support multiple organizations, scoped RBAC, configurable terminology and role titles, capacity-controlled registration, optional waiting lists, paid features, announcements, attachments, optional chat, and themes.

## 2. Technology stack and hosting

The planning baseline is Go with Chi for the HTTP API; TypeScript, React, and Next.js for the frontend; PostgreSQL for persistence; pgx and sqlc for typed database access; and Caddy for HTTPS and reverse proxying. Next.js supports server-rendered public event pages for search visibility. Chi uses Go’s standard net/http conventions. Caddy simplifies HTTPS on a directly managed server.

Deployment must use direct Linux installation, without Docker or containers. The initial host is DigitalOcean; the design should allow a later move to AWS or another provider. Proposed deployment uses a Go executable and a Node.js/Next.js process managed by systemd, with Caddy installed directly. Managed PostgreSQL is preferred; local PostgreSQL remains an option. Exact versions, Linux distribution, database hosting, and infrastructure sizing remain open.

The Go application must use structs, methods, interfaces, and composition to model domain objects. CRUD operations must enforce business rules, permissions, and applicable subscription entitlements. Approval, cancellation, chair appointment, and waiting-list promotion should be explicit domain actions rather than unrestricted field updates.

## 3. Domain model

- User account: a person’s identity at one organization, credentials, email verification state, and profile. A person has one login per organization (4A.7).
- Organization: owns memberships, policies, events, titles, communication, and subscription settings.
- Organization membership: connects a person’s account to its organization with organization-specific roles. Paid access belongs to an event (3A.2, 7C), not to the membership. A person in several organizations has an account at each (4A.7).
- Event: a named activity owned by one organization, containing stations and governed by an event board. Example names include Halloween Bash and Valentine Dance.
- Event board: event governance body with a chair and configurable membership capacity. Capacity includes the event chair.
- Board membership: a person’s appointment to an event board and role within it.
- Station: a named part of an event with a chair and configurable member capacity. Capacity includes the station chair.
- Event registration: a person’s participation in an event, subject to organization registration policy.
- Station assignment: a registered person’s participation in a station, subject to event assignment and station capacity rules.
- Waiting-list entry: an optional request for a full station, with lifecycle and promotion rules to be defined.
- Role and permission assignment: grants capabilities at system, organization, event, or station scope.
- Subscription plan and organization subscription: define purchased organization-level capabilities and seat entitlements.
- Seat allocation and individual payment: track organization-funded or individually funded access under an organization’s subscription arrangement.
- Announcement: scoped communication with links and supported attachments/media.
- Attachment: a file with ownership, metadata, visibility, and access rules tied to its parent scope.
- Conversation, participant, and message: optional chat resources at organization, event, station, or direct-message scope.
- Theme: a color palette with optional font-family and layout settings.

Relationships must preserve ownership: stations belong to events; events belong to organizations; registrations and station assignments cannot cross organization boundaries. Proposed technical entities include authenticated sessions, one-time verification/reset tokens, audit records, email-delivery jobs, and payment-provider event records.

## 4. Organization isolation and authentication context

A person may hold an account at several organizations, one at each (4A.7), but may access only one organization at a time. The user must log out of the current organization and log into another to change organization context. There must be no silent organization switch that retains the prior organization session.

Every protected request, file request, search, notification feed, and live chat connection must be checked against the currently authenticated organization and scoped permissions. Logging out must invalidate the relevant session and close associated live connections. A user’s role in one organization must not grant authority in another.

Public event pages are an explicitly permitted exception to authenticated membership access: organizations control which event information is public. Private organization information must not be exposed through public pages, search metadata, caches, or public attachment URLs.

The exact meaning of “one organization at a time” across multiple browsers/devices, and how organization selection fits a two-field login screen, remain open. Proposed design binds the server-side session to an organization, rather than trusting an organization ID supplied by the client.

### 4A.1 Each organization has its own login address (Confirmed)

**How one organization per browser (4A.2) holds across subdomains (Confirmed).** The owner accepted this on October 8, 2026. A cookie is a small piece of data a site stores in the browser, which the browser sends back on later visits.

1. When a person logs in at an organization's address, the server sets two cookies.
   - **The sign-in cookie,** for that address only. It keeps the person logged in to that organization. The browser sends it back only to that address.
   - **The organization cookie,** `pe_org`, set for the shared part of every organization's address. Its value is the organization's address name. The browser sends it to every address that ends in that shared part.
2. When the same browser opens a second organization's address, the server reads `pe_org`. If it names another organization, the server shows the second organization's login screen with "You are logged in to [ORGANIZATION NAME]" and a Log out button, and refuses a login there.
3. Logging out deletes both cookies.
4. The organization cookie only says which organization the browser is in. It grants nothing. Access comes from the sign-in cookie, which the server checks on every request.

Example: Dana logs in at `lincolnpta.phoenixevent.tomsherlock.space`. The server sets her sign-in cookie for that address, and `pe_org=lincolnpta` for `phoenixevent.tomsherlock.space`. She then opens `riverside.phoenixevent.tomsherlock.space` in the same browser. Her browser sends `pe_org=lincolnpta` there, so she sees Riverside's login screen with "You are logged in to Lincoln Elementary PTA" and a Log out button. Once she logs out, both cookies are gone and she can log in to Riverside.

**How the rule holds at an address an organization owns (Open, held by the owner).** A browser sends a cookie only to the site that set it. A server at `events.lincolnpta.org` therefore never receives `pe_org` from `phoenixevent.com`, and cannot tell which organization the browser is logged in to there. Two approaches were put to the owner on October 8, 2026, and the owner accepted neither and holds the decision:

- Accept the gap: the rule holds across all `phoenixevent.com` addresses, and an organization's own address counts separately.
- Send every login at an organization's own address through `login.phoenixevent.com`, which reads `pe_org` and then returns the person to the organization's address.

This arises only when organizations use their own addresses, after the first release.

## 5. Governance, capacity, and registration

Each organization controls an event through its board, headed by a chair. Board membership capacity is configurable and includes that chair. Each station has a chair and configurable capacity that includes its chair. Appointment, replacement, and removal actions must preserve these limits.

Organization policy determines registration conditions, including any approval requirement. Organization configuration also determines whether a person may join multiple stations in one event. A proposed representation is maximum stations per participant per event, with a value of one for single-station participation, a higher limit, or unlimited; the default and available policy options need confirmation.

Full stations may offer an optional waiting list. The confirmed governance rule is:

- If the organization prohibits waiting lists before the event board is formed, the board cannot enable them.
- If the organization requests a waiting list before board formation, the board may disable it.
- If the organization makes no prior determination, the board may enable or disable waiting lists.

Record the prior organization determination and board decision separately. Policies after board formation, authority to change an earlier prohibition, list ordering, promotion, acceptance deadlines, and handling existing entries when disabling a list are unresolved.

Proposed implementation uses PostgreSQL transactions and constraints/locking to prevent concurrent assignments from exceeding capacity or creating duplicate registrations. Whether pending registrations reserve capacity, and whether board or station chairs must have event registrations, must be decided before final schema design.

## 5A. Event creation governance

### 5A.1 Requirement (Confirmed)

Organizations differ in who may bring an event into existence, and the application must support each organization's own policy. The owner's examples:

- A corporation works top down. The CEO creates an event, or the board of directors does, or a committee drawn from the board, or a research committee of executives, employees and perhaps one director, or the chair of the event board.
- A volunteer organization, community organization or charity works by proposal. Employees, executives or directors propose an event, and the board of directors, the CEO, the C-suite, or a majority of employees approves it.

For-profit and non-profit organizations are major variants of this requirement.

### 5A.2 Terms and model

**Terms the owner has set. (Confirmed)** Section 3A gives them in the owner's words.

- **Registrant:** someone who registers to participate in the event.
- **Subscriber:** someone who pays to participate in the event.
- **Participant:** someone who participates in the event, regardless of whether they registered or subscribed.

**Terms from sections 1 to 3, used here as those sections use them.**

- **Organization:** a PTA, community committee, bank, business or similar, which owns its members, events and policies.
- **Member:** a person who belongs to an organization.
- **Event:** a named activity owned by one organization, such as Halloween Bash.
- **Station:** a named part of an event, such as Face Painting.
- **Chair:** the person who heads an event board or a station.
- **Event board:** the group that governs one event.

**Terms this section adds. (Confirmed)**

- **Body:** a named group of members inside one organization, such as the Board of Directors, the C-suite, an Events Committee, a Research Committee, or All Employees. Each organization names its own bodies and decides who is in each. A body may have a chair. "Body" is a working word and the owner may rename it.
- **Proposal:** a member's request that an event be created, waiting for approval.
- **Proposer:** the member who makes a proposal.
- **Approver:** a member who has a say in whether a proposal goes ahead.
- **Event creation rule:** one statement of an organization's policy on who may create events. Example: "Any employee may propose an event, and the Board of Directors approves by majority."

**The model. (Confirmed)**

Every organization writes its policy as one or more event creation rules. Each rule answers five questions.

| Question | Possible answers |
| --- | --- |
| 1. Who may start an event? | People holding a named role, the members of a named body, a named member, or every member |
| 2. Does the event exist at once, or does it need approval? | **Create directly:** the event exists at once. **Propose:** the event exists after approval. |
| 3. Who approves? (when the answer to 2 is Propose) | People holding a named role, the members of a named body, or a named member |
| 4. How do the approvers decide? (when the answer to 2 is Propose) | **Any one approver** says yes. **All approvers** say yes. **A share of the approvers** says yes, such as more than half. A rule may also set a quorum, which is a minimum number of approvers who must have voted. |
| 5. Which comes first, the board or the chair? | **The board first:** the Organization appoints the board members, and they choose a chair from among themselves. **The chair first:** the Organization appoints the chair, and the chair appoints the board members. Section 5E gives the rule. |

An organization may hold several rules at once, and a member may use any rule that names them. Example for a corporation with two rules:

- "The CEO may create an event directly."
- "Any employee may propose an event, and the Board of Directors approves by majority."

Under these two rules the CEO creates an event with no approval, and an employee's event exists only after the board approves it.

For-profit and non-profit organizations use the same five questions with different answers. The application treats them the same way and reads each organization's own rules.

### 5A.3 The owner's examples as rules (Confirmed)

| Example | Who may start | Create directly or propose | Who approves | How they decide |
| --- | --- | --- | --- | --- |
| The CEO creates an event | The CEO | Create directly | Nobody | No decision needed |
| The board of directors creates an event | Members of the Board of Directors | Propose | The Board of Directors | More than half of the board |
| A board committee creates an event | Members of the Events Committee | Create directly | Nobody | No decision needed |
| A mixed research committee creates an event | Members of the Research Committee | Create directly | Nobody | No decision needed |
| The chair of an event board creates an event | An Event Chair | Create directly | Nobody | No decision needed |
| Staff propose, the board approves | All Employees | Propose | The Board of Directors | More than half of the board |
| Staff propose, the CEO approves | All Employees | Propose | The CEO | Any one approver |
| Staff propose, the C-suite approves | All Employees | Propose | The C-suite | The organization chooses for this rule: any one approver, all approvers, or a share |
| Staff propose, a majority of employees approves | All Employees | Propose | All Employees | More than half of all employees |

In the second example a director proposes and the whole board votes. Whether one director may instead create the event alone, acting for the board, is Open and is answered rule by rule.

A new organization starts from one of two ready-made sets of rules and edits them afterward:

- **Direct:** organization administrators create events directly.
- **Propose and approve:** every member may propose, and one named body approves.

### 5A.4 The life of a proposal (Confirmed)

A proposal is in one of five states: Draft, Submitted, Approved, Declined, or Withdrawn.

**Writing a draft.** A member may start a draft only when their organization has a rule, currently switched on, that lets them propose events. Example: the organization's rule says "any employee may propose an event, and the Board of Directors approves". An employee may start a draft. A member who is not an employee, and whom no other rule names, may not: the "Propose event" button is absent for them and the server refuses the action.

The draft holds the proposed event's details: its name, date, location, description, who can see it, and the size of its event board. These are the fields of the Create event screen (S1). Only the proposer can see or change a draft, and the proposer may save it as many times as they like.

**Submitting.** When the proposer submits, the application does seven things in order. If any one of them fails, the proposal stays a Draft and nothing else changes.

1. **It checks the event details.** The event has a name, and the event board has room for at least 1 person.
2. **It finds the rule that applies.** It looks at the organization's switched-on rules that let this person propose today. With one such rule, that rule applies. With several, the proposer picks one on the Propose event screen (G3), which shows each rule by who would approve. With none, the application refuses.
3. **It lists the approvers by name.** A role becomes everyone who holds that role today. A body becomes everyone in that body today. A named member is that member. Each person appears once. The number of people on the list is called N. With nobody on the list, the application refuses.
4. **It works out how many approvals are needed.** This number is called R and comes from the table below.
5. **It records the result on the proposal:** which rule applied, how the approvers decide, any quorum, which comes first, the board or the chair, the list of approvers, N, R, and the time.
6. **It marks the proposal Submitted.** From now on the event details are locked.
7. **It emails each approver** a link to the Proposal review screen (G4).

Example: an employee submits under the rule "any employee may propose, and the Board of Directors approves by majority". The board has 7 directors today. The approvers are those 7 people, N is 7, and R is 4.

**Why the list is recorded.** The approvers, N and R written down at step 5 decide the proposal. If the organization later edits the rule, gives the role to someone new, or adds a director, this proposal keeps the approvers and numbers it was submitted with. The one exception is an approver who is removed, covered in 5A.8.

**A proposer who is also an approver.** A director who proposes to their own board stays on the list of approvers and votes like every other director.

**Deciding.** Each approver either approves or declines, and may add a comment. An approver may change their answer while the proposal is Submitted.

The outcome is counted from five numbers. **N** is the number of approvers on the recorded list. **A** is the number who currently approve. **D** is the number who currently decline. **U** is the number yet to answer, so N = A + D + U. **R** is the number of approvals needed.

- The proposal becomes Approved the moment A reaches R.
- The proposal becomes Declined the moment A + U falls below R. At that point R is out of reach even if every remaining approver approved.
- Either outcome is final. Answers arriving after it are refused.

| How the approvers decide | R, approvals needed | Approved when | Declined when |
| --- | --- | --- | --- |
| Any one approver | 1 | 1 approver approves | Every approver has declined (D = N) |
| All approvers | N | Every approver has approved (A = N) | 1 approver declines |
| A share, more than P percent | The smallest whole number greater than P percent of N | A = R | D = N - R + 1 |
| A share, at least P percent | The smallest whole number equal to or greater than P percent of N | A = R | D = N - R + 1 |

Worked examples for "more than half":

| Approvers (N) | R | Approved at | Declined at | A tie |
| --- | --- | --- | --- | --- |
| A board of 7 | 4 | The 4th approval | The 4th decline | Cannot occur |
| A board of 6 | 4 | The 4th approval | The 3rd decline | 3 to 3 is declined |
| All Employees, 40 people | 21 | The 21st approval | The 20th decline | 20 to 20 is declined |

- A share is measured against all N approvers. An approver who never answers counts toward neither side, so a proposal can stay Submitted until it is withdrawn or a deadline closes it. Deadlines are Open in 5A.10.
- A quorum Q, when a rule sets one, adds a second condition for approval: A + D must reach Q. With a share measured against all N approvers, a quorum changes the outcome only when Q is greater than R.

**Withdrawing.** The proposer may withdraw a proposal that is a Draft or Submitted. A Withdrawn proposal creates no event and accepts no further answers.

**Approval creates the event.** The moment a proposal becomes Approved, the application creates the event from the proposal's details and links the two. Both happen together: a proposal is never Approved without its event, and one proposal never produces two events.

**Choices in this section with Open alternatives.**

- At step 2, the organization could rank its rules, so that the highest-ranked rule applies and the proposer makes no choice.
- The organization could bar a proposer from voting on their own proposal, which lowers N by 1.
- A share could be measured against the answers given (A + D) instead of all N approvers. That decides faster, and it needs a quorum and a deadline to be safe.
- For "any one approver", the first answer of either kind could settle the proposal.

### 5A.5 What the application keeps (Confirmed)

- **Bodies:** each body's name, its members, and its chair if it has one.
- **Event creation rules:** each rule's five answers from 5A.2, and whether the rule is switched on.
- **Proposals:** who proposed, the proposed event's details, which rule applied, the recorded approvers with N and R, the state, the times, and the event that resulted.
- **Decisions:** which approver answered, whether they approved or declined, their comment, and when. Each approver has one current answer per proposal.

Each body, rule, proposal and decision belongs to exactly one organization. A body, rule, proposal or decision in one organization is invisible to every other organization, in line with section 4.

### 5A.6 Who may do what (Confirmed)

Five permissions cover this section.

1. Create an event directly.
2. Propose an event.
3. Decide a proposal.
4. Manage the organization's event creation rules.
5. Manage the organization's bodies.

### 5A.7 Actions (Confirmed)

### 5A.8 Rules that hold for every organization (Confirmed)

- An event comes into existence in two ways only: a member creates it directly, or an approved proposal creates it.
- A member may use a rule only while the rule still names them at the moment they act. Example: an employee who leaves the organization's staff can no longer start a draft under "any employee may propose".

- When an approver is removed from the organization or from the approving body, their answer stops counting. Whether N and R are then worked out again for the smaller group is Open.
- Two approvers answering at the same moment produce one outcome and at most one event.
- An organization always has at least one rule switched on, so that events can be created.

## 5B. Joining a station

Recorded October 5, 2026, from the owner's statement. This is a business rule. It is recorded here for development in Claude chat or Claude Code. The wireframes show it on screens 4, 7, 8 and 9.

### 5B.1 The rule (Confirmed)

1. **Who may ask.** A user may submit a request to join a specific station. The user may be a registrant, a subscriber, a member or a worker.
2. **Joining at once.** Joining a station may mean that the user becomes a member of the station upon submitting the request, if the station has open spots.
3. **Joining with approval.** Joining a station may instead require approval. The approver is the station's chair, station lead or station manager.
4. **When that position is open.** If the station has nobody in that position yet, the responsibility for approving falls to the Event Board Chair.

Example: Haunted Hallway has 9 of 10 spots taken and Dana Reyes is its Station Chair. If Haunted Hallway lets people join at once, a user who asks to join takes the 10th spot immediately. If Haunted Hallway requires approval, the request goes to Dana Reyes. If Haunted Hallway had no chair yet, the request would go to the Event Board Chair of Halloween Bash.

### 5B.2 How this fits what is already recorded

- **Capacity.** Section 5 says a station's capacity includes its chair and that assignments cannot pass capacity. Joining at once and joining by approval both stay inside that limit.
- **Stations per person.** Section 5C sets no limit on how many stations one person may join in an event. Each station's capacity is the only limit.
- **Waiting lists.** Section 5 covers what a full station may offer. This section covers a station with open spots.
- **Role titles.** Section 6 says role titles are display text that an organization or event may rename. "Station chair", "station lead" and "station manager" are read here as three titles for the one position that heads a station. This reading is Proposed (see 5B.4).

### 5B.6 A waiting request holds a spot, with an expiry

Recorded October 5, 2026, from the owner's choice among three options. This settles the item "Holding a spot" that 5B.4 listed, and it applies to stations that require approval.

**The rule. (Confirmed)**

1. **A waiting request holds 1 spot.** From the moment a user sends a request to join, the request holds 1 of the station's spots until it is decided.
2. **A held spot counts as taken for everyone else.** The spots open to new requests are the station's capacity, less the spots taken, less the spots held.
3. **The hold has an expiry.** A request that receives no answer by its expiry time lapses. The spot it held opens again.

Example: Face Painting has a capacity of 12, with 11 spots taken. Dana asks to join, and her request holds the 12th spot. Sam asks to join a minute later. For Sam the station is full, and section 5's waiting list rules apply. If the Station Chair approves Dana, she takes the spot her request held. If the Station Chair declines her, or her request lapses, the spot opens and the station shows 11 of 12 spots taken again.

**How it works. (Proposed)**

- A request is in one of five states: Pending approval, Approved, Declined, Lapsed or Withdrawn. Only a request that is Pending approval holds a spot.
- Approving a request always succeeds on capacity, because the spot is the one the request already holds.
- The user sees the expiry time on their waiting request (screen 8), and the approver sees it beside each request (screen 9).
- When a request lapses, the user is told by email.
- Two users who send requests for the last open spot at the same moment produce one held spot. The other user finds the station full.

**Effect on the wireframes.**

- **Screen 7:** states that the request holds 1 spot while the user waits, and that it lapses at the expiry time.
- **Screen 8:** the waiting panel shows the expiry time and the spot held, and a third outcome, Lapsed, is drawn beside Approved and Declined.
- **Screen 9:** each request shows its expiry time, and the Spots panel shows the spots held as well as the spots taken.

**Open decisions.**

- **The length of the expiry,** and who sets it: the application, the organization, or the event board.
- **A reminder.** Whether the approver is reminded before a request lapses.
- **After a lapse.** Whether the user may ask again at once.
- **Capacity lowered while requests wait.** What happens to held spots when the event board lowers a station's capacity below the spots taken plus the spots held.
- **Promotion from the waiting list.** When a held spot opens through a decline or a lapse, whether it goes first to the station's waiting list.

## 5E. The order: event, then board and chair

## 6. Configurable vocabulary and titles

Default domain labels include event and station. Administrators must be able to substitute terms such as function, activity, festival, or department. Labels are distinct from individual names: Festival may be the label while Halloween Bash is the event name. Internal resource identifiers and permission names remain stable when labels change.

Terminology configuration scope remains undecided. Singular/plural forms and consistent use in forms, navigation, announcements, emails, and accessibility labels are proposed requirements for implementation review.

Role titles, such as Event Director, Event Chair, Event Executive, and Event Manager, are initialized at organization level and may be overridden at event level. If an event has no override, it inherits the organization title. Renaming a displayed role title must not alter RBAC permissions. Whether inherited titles update immediately after organization changes remains open.

## 7. RBAC, CRUD, and paid entitlements

Support role-based access control with system, organization, event, and station scopes. Organization leadership, organization administrators, event administrators/boards/chairs, and station chairs need separately definable permissions. Exact roles and the permission matrix remain to be finalized; examples in this specification do not grant automatic unrestricted access.

CRUD applies to domain resources, with relationship and lifecycle rules enforced. Deletion versus archival, retention, reassignment of chairs, and removal of resources that already have memberships, registrations, files, or payment history require explicit policy decisions.

Paid entitlements and RBAC are separate checks. A paid subscription does not itself grant administrative permission, and administrative permission does not automatically bypass a paid entitlement. Rules for overrides or complimentary access remain open.

Payments belong to events. An individual payment or an organization payment covers participation in an event (3A, 7C). Organization membership and paid-access state must be represented separately.

Unresolved billing rules include hybrid seat/individual-payment arrangements, the scope of an individual purchase across organizations, who counts against seat limits, plan prices, renewal/cancellation, expiration behavior, refunds, and the payment provider. The full set of paid features will be revisited. Chat is normally subscription- or upgrade-gated.

- **What the System Administrator sees.** What an Organization Administrator of that organization sees, in that organization only. Every other organization stays closed to them.
- **The banner.** Every page in a support session carries a banner naming the organization and the time the access ends.
- **The record.** The organization keeps a record of each time support access was opened: who opened it, the reason they gave, when it opened and ended, how it ended, and which System Administrator entered. Organization Administrators can read this record on screen O5.
- **Ending.** At the end time, or when the organization ends access early, the support session stops at once and the System Administrator's next request is refused.

## 7C. Payments

Restated October 6, 2026 in the owner's terms (section 3A). It replaces the earlier text of this section, which described paid seats for members of an organization. That text stays in versions 0.23 to 0.28.

### 7C.1 Two kinds of payment (Confirmed)

## 9. Public pages and discoverability

Public event pages must support strong search-engine visibility. Organizations must be able to hide events when they prefer. Proposed visibility modes are public/indexable, unlisted/noindex, and private/authenticated; the final vocabulary and controls need approval.

Server-rendered content, page titles/descriptions, canonical URLs, and sitemaps should reflect the effective visibility. Hiding an event must remove its private information and files from public responses. Search exclusion alone does not protect confidential content. Previously indexed content may remain in external search caches after visibility changes.

## 10. Optional chat

Chat must support organization conversations, event conversations, station conversations, and direct messages. It is optional and can be activated by a role with the required permission, such as a system administrator. Access is normally unlocked by a subscription payment or upgrade payment.

Direct messages are permitted only among people who belong to the currently logged-in organization. Membership shared elsewhere is insufficient for a message in the current organization context. Group access follows the corresponding organization/event/station membership and RBAC rules.

Chat must not support attachments. Activation scope, moderation, message retention/deletion, history after membership removal, notifications, and behavior when entitlement expires remain open. Proposed implementation uses authenticated live connections and persists messages in PostgreSQL; the transport and delivery guarantees remain implementation choices.

## 11. Attachments and announcements

Support still-image uploads in jpg, jpeg, and png, and documents in md, html, pdf, doc, and docx. Attachments are supported at organization, event, and station levels; chat attachments are excluded. Access follows the parent’s organization, scope, permissions, and effective visibility.

Announcements pages exist at organization, event, and station levels. Authorized organization leadership/c-suite and the relevant chairs can post announcements according to scoped RBAC. Announcements support downloadable documents, displayed images, uploaded playable videos, embedded external videos, and internal/external links.

Clicking an external link must show a warning with the destination and allow the user to continue or cancel. Internal links must still enforce access checks. External video embeds are supported; a notice before loading third-party content is a proposed behavior, not yet a separately confirmed policy.

Proposed file handling includes actual-type validation, configured size limits, generated storage identifiers, sanitized HTML/Markdown previews, and permission checks on downloads. Preview/conversion of doc/docx and PDF files, upload scanning, storage service, retention, and quotas remain design decisions. Arbitrary uploaded scripts or unsanitized HTML must not execute in the application origin.

Supported video formats and upload size limits are explicitly pending task-review items.

## 12. Themes, icons, and accessibility

Support configurable color palettes and optionally layouts and font families. The three built-in themes are Sunbeam (light), Moonshadow (dark), and Greystone (neutral colors intended for colorblind users). System administrators, organization administrators, and event administrators can add themes within their authorized scope.

Levels, states, and locations may be represented by icons paired with theme colors. Proposed accessibility rules require text/accessible labels and readable contrast, with meaning preserved without color alone. Greystone’s palette must be evaluated for accessibility rather than assumed accessible solely because its colors are neutral.

Open decisions: theme inheritance and precedence, whether users may choose personal themes, admin restrictions on overrides, layout customization boundaries, font provisioning, and icon/label/color mappings.

## 13. Proposed architecture and operational requirements

Start with a modular Go application rather than independently deployed services. Separate identity/session, organization authorization, event governance, registration, billing entitlements, communication, media, and presentation configuration into domain modules. Domain services enforce invariants; persistence adapters use pgx/sqlc; external adapters handle email, payment, and file storage. This organization is proposed and may change with the high-level architecture.

Use PostgreSQL migrations with tenant ownership recorded on organization-scoped resources. Proposed defenses include ownership constraints, centralized authorization, and optional row-level security after a design review. Protect tenant boundaries in background jobs, caches, live connections, search, and file delivery as well as API handlers.

Proposed operational capabilities include structured logs, health checks, audit records for sensitive administrative actions, email retry handling, database backups with restore exercises, and documented upgrades/rollback. Performance objectives, availability, recovery targets, retention, and expected organization/event sizes are not yet set.

## 15. Acceptance criteria

- A user belonging to two organizations can access only the authenticated organization’s protected resources; access to another requires logout and a new organization login.
- Server-side requests and file/chat access cannot be authorized by changing a client-supplied organization identifier.
- Chair appointments count against station/board capacity, and simultaneous assignments cannot overbook a station.
- The configured multiple-station rule is enforced per participant and event.
- Waiting-list decisions follow all three confirmed governance cases, including a pre-board prohibition that the board cannot override.
- Organization role titles appear by default; event overrides change display text without altering permissions.
- Login has the specified two fields, password visibility control, and reset link; omitted usernames default to email.
- Chat works at all four requested scopes, checks permissions/entitlements, restricts direct messages to the active organization, and rejects attachments.
- Supported images/documents attach to organizations, events, and stations with scoped downloads; announcements support both uploaded and embedded video.
- External-link navigation requires the destination warning and can be cancelled.
- Public event pages expose intended search content; private events and attachments reject unauthorized access.
- Sunbeam, Moonshadow, and Greystone preserve icon/text meaning and meet the agreed accessibility target.
- Deployment and documentation use direct installation without containers, and final guides are downloadable in all three formats.

Acceptance criteria that depend on open policy choices will be expanded when those choices are settled. A successful login or build alone is insufficient to establish full application readiness.

## 15A. Acceptance criteria added

- An organization configured with the Direct preset lets an organization administrator create an event at once, and offers other members no create or propose action.
- An organization configured with Propose and approve lets a member submit a proposal, and the event exists only after the named body's decision rule is met.
- Each example in section 5A.3 can be configured through rules alone, with no code change.
- A proposal submitted under one rule is decided under that rule after the organization edits its rules.
- Two approvers deciding at the same moment produce exactly one event.
- A member of one organization cannot see or decide a proposal in another organization, including by changing a client-supplied identifier.
- The Organization home button reads "Create event", "Propose event", or is absent, according to the rules the person matches.
- Each organization's login address shows that organization's login screen, and a successful login there opens that organization only.
- A person logged in to one organization who opens a second organization's address in the same browser reaches the second organization only after logging out of the first.
- A person may be logged in to two organizations at once in two different browsers.
- A person may join every station in an event that has an open spot, with no limit on the number of stations.
- A station's capacity is set by the event board of its event, and an organization has no setting that limits stations per person.
- A person appointed Event Board Chair, Event Board Member, Event Administrator or Station Chair is a participant of that event from the moment of appointment, and never appears in the approval queue.
- A request to join a station that requires approval holds 1 spot from the moment it is sent until it is approved, declined, withdrawn or lapsed.
- A user who asks to join a station whose remaining spots are all held by waiting requests is treated as asking to join a full station.
- A request with no answer by its expiry time becomes Lapsed, and the spot it held is open to the next request.
- How a station is joined, at once or with approval, is set for each station by the event board of its event, and two stations of one event may differ.
- A person who is yet to be a participant of an event is refused when asking to sign up for one of its stations, in every organization.
- A newly created event has no board and no chair, and is listed as the Organization's event.
- Under a rule set to "the board first", the chair can be chosen only from the appointed board members. Under a rule set to "the chair first", board members can be appointed only once the event has a chair, and the chair appoints them.
- Adding a member to a body, or removing one, changes no event board.
- An individual payment made in one organization gives nothing in a second organization.
- An organization set to take subscribers offers no registration, one set to take registrants offers no individual payment, and one set to take both offers each.
- A person the organization pays for in an event is a participant of that event and is asked for no individual payment.
- An individual who makes an individual payment for an event is a subscriber and a participant of that event.
- A station may be created with no Station Chair. Its chair is then either appointed by the event board or voted in by the station's members.
- A System Administrator who requests an organization's members, events or messages while that organization's support access is closed is refused.
- A support session can start only after an Organization Administrator of that organization opens support access, and it stops when the access ends.

## 16. Roadmap

This roadmap is a proposed sequence, not a calendar commitment. Features below remain in scope even when deferred to later phases. No duration estimates are assigned until architecture, staffing, and release scope are known.

### Phase 0 — resolve foundational decisions

Deliver a reviewed requirements baseline, domain lifecycle diagrams, tenant/session model, permission matrix, entitlement model, and chosen initial release scope. Select the repository name/ownership, runtime versions, and direct-host deployment targets. Resolve organization login behavior, capacity reservation, chair membership, and payment/membership rules before committing to the schema.

Exit: high-level architecture and outstanding assumptions are explicitly reviewed; no proposed policy is silently treated as confirmed.

### Phase 1 — repository and development foundation

Create the new repository and modular Go/Next.js structure. Set up PostgreSQL migrations, sqlc generation, direct local setup, automated checks, configuration handling, and initial deployment documentation. Keep legacy repositories as references. Select an email adapter and file-storage interface.

Exit: repeatable non-container developer setup, API/frontend builds, migration execution, and health checks pass.

### Phase 2 — accounts, organization context, and RBAC

Implement accounts, username/email rules, verification/reset, login/logout, memberships, scoped authorization, and active organization sessions. Add server-side isolation and session tests. Define system-versus-organization administrator boundaries.

Exit: cross-organization access is denied across API, UI, files, and session transitions; verified authentication flows work with a test email service.

### Phase 3 — events, boards, stations, and registration

Implement CRUD/lifecycle actions, role titles, chairs, capacities, registrations, station assignments, organization registration policies, and optional waiting lists. Add concurrency checks and policy tests. Implement agreed terminology controls.

Exit: realistic event setup and registration work, capacity/duplicate constraints hold under concurrent requests, and waiting-list governance is enforced.

### Phase 4 — public pages, announcements, media, and themes

Implement public visibility/SEO, attachments, announcements at all levels, external-link warnings, video uploads/embeds, and the three basic themes. Add configured theme extensions, icon mappings, accessible forms, and scoped media delivery.

Exit: public/private behavior, supported downloads/media, external navigation, and accessibility are validated against agreed limits and policies.

### Phase 5 — subscriptions and individual payment

Implement organization plans, seat allocation, individual-funded access, paid entitlements, provider integration, and audited billing transitions. Implement the selected expiration and cancellation policies. Test payment event retries and idempotency.

Exit: agreed billing models work without mixing membership, payment state, and authorization, and replayed provider events cannot duplicate access/payment changes.

### Phase 6 — optional chat

Implement organization/event/station/direct conversations, authorized activation, paid gating, live session checks, and the agreed moderation/retention behavior. Enforce attachment exclusion and current-organization direct messaging.

Exit: live and historical access respect organization/session boundaries, logout terminates access, and subscription/permission gates behave correctly.

### Phase 7 — release validation and direct deployment

Run end-to-end workflows, accessibility review, tenant isolation checks, concurrency/load checks, backup restoration, and upgrade/rollback exercises. Finalize direct installation instructions in Markdown/HTML/PDF and deploy to an agreed staging host before production release.

Exit: required checks pass or diagnosed defects are explicitly accepted for release; tested documentation, support procedures, and production approval are complete. Source commits, environment activation, downloadable documents, and live deployment are distinct actions and must be reported separately.
